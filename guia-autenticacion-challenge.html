02Fundamentos

HTTP, identidad y límites de confianza

Tu navegador y Flask son procesos separados. El navegador envía una petición con método, ruta, cabeceras y, a veces, un cuerpo JSON. Flask devuelve una respuesta con código de estado, cabeceras y cuerpo. Cada petición debe traer suficiente información para decidir si puede acceder al recurso: HTTP no recuerda por sí solo el login anterior.

  1. 01Navegador

    fetch("/user/profile") envía una petición.

  2. 02Servidor

    Flask selecciona la ruta y verifica la credencial.

  3. 03Almacenamiento

    Se busca la sesión o se valida el token; el perfil consulta users.

  4. 04Respuesta

    Se devuelve JSON y el frontend lo presenta.

Autenticación: ¿quién eres?

El login verifica una contraseña. Las siguientes peticiones presentan una credencial derivada: un identificador de sesión o un token. Conocer un email no prueba la identidad.

Autorización: ¿qué puedes hacer?

Después de identificarte, el servidor decide si puedes ejecutar la operación. Un usuario válido no tiene por eso permiso para listar o eliminar otras cuentas.

Límite de confianza: todo lo que manda el cliente puede manipularse. Un botón oculto, un campo deshabilitado o una variable currentUser.role no son controles de acceso. El servidor debe repetir las comprobaciones relevantes en cada ruta.

Los códigos que debes reconocer

200: éxito. 201: cuenta creada. 400: datos inválidos. 401: falta una credencial válida. 403: permiso insuficiente o CSRF rechazado. 404: recurso inexistente. 409: email duplicado. 415: formato de cuerpo no admitido. 429: bloqueo por intentos. 500: fallo inesperado del servidor.

En tu implementación /auth/status devuelve 200 con authenticated: false si no reconoce la sesión; eso es diferente de la respuesta 401 de una ruta protegida.

HTTPS / TLS

HTTPS protege la confidencialidad e integridad del tráfico y autentica el servidor mediante certificados. Debe cubrir el login y las peticiones posteriores. No cifra automáticamente el contenido de un JWT cuando ya está en manos del cliente, ni soluciona XSS o una autorización incorrecta.

03Fundamentos

Hashing, cifrado, firma y contraseñas

Estas operaciones resuelven problemas diferentes. Una de las preguntas más importantes de tu challenge es distinguirlas sin mezclarlas.

OperaciónQué consigueEjemplo y límite
CodificaciónCambia la representación de datos.Base64url en un JWT; cualquiera puede decodificarla, no hay una clave secreta.
Hash de contraseñasPermite verificar una contraseña sin almacenarla en claro.bcrypt; no tiene una operación de descifrado, pero un atacante puede probar candidatos.
CifradoOculta datos usando una clave; el destinatario autorizado puede recuperarlos.JWE o cifrado autenticado mediante una biblioteca mantenida; no inventar un protocolo propio.
Firma / MACDetecta modificaciones y acredita al emisor según el modelo de claves.HS256 usa HMAC con clave compartida. No es una firma asimétrica y no oculta el payload.

Está en routes/auth_routes.py:45 y routes/auth_routes.py:82. El hash contiene la información de salt y coste que necesita checkpw. No comparas dos hashes generados con salts nuevos; usas la función de verificación.

El salt no necesita ser secreto y hace que dos contraseñas iguales puedan producir hashes diferentes. El coste encarece cada intento. Aumentarlo exige medir el tiempo y la carga del servidor; no es simplemente “más siempre es mejor”. Un pepper sería un secreto adicional guardado fuera de la base de datos; tu código no lo usa.

El requisito de longitud actual es ocho caracteres. No hay validación explícita de tipos ni límite en bytes antes de bcrypt. La familia bcrypt tiene un límite de 72 bytes: con la versión 4.1.2 declarada puede truncar entradas largas. Dos contraseñas que comparten esos primeros bytes pueden volverse equivalentes. Hay que definir una política compatible y probar Unicode, porque caracteres y bytes no son lo mismo.

Corrige esta frase al defender

“Irreversible” no significa “imposible de adivinar”. Una contraseña débil puede descubrirse probando candidatos contra el hash. El comentario que afirma que nadie puede recuperar la contraseña es demasiado absoluto.

Para diseños nuevos conviene conocer Argon2id; bcrypt sigue siendo el algoritmo que usa tu entrega. No cambies de algoritmo sin planificar la migración de hashes y medir recursos. La contraseña debe viajar mediante HTTPS aunque se guarde hasheada.

04Fundamentos

Cookies: qué guardan y cuándo viajan

Una cookie es un dato que el navegador conserva y adjunta a peticiones que cumplan sus reglas. En tu aplicación se llama sessionId y contiene un UUID opaco: el email, el rol y el token CSRF quedan del lado del servidor.

HTTP/1.1 200 OK
Set-Cookie: sessionId=<identificador>; Path=/; Max-Age=86400; HttpOnly; SameSite=Strict
Content-Type: application/json

{"authMethod":"cookie","csrfToken":"<token-csrf>"}

El ejemplo refleja el modo de desarrollo actual. En producción debe añadirse Secure y servirse por HTTPS. En una petición posterior el navegador manda Cookie: sessionId=…; no reenvía los atributos de seguridad como parte de ese encabezado.

AtributoSignificadoSituación en tu código
HttpOnlyImpide leer la cookie con JavaScript; el navegador todavía la envía.Siempre True. No impide que un XSS ejecute acciones autenticadas.
SecureRestringe el envío a HTTPS, con particularidades locales del navegador.Solo True si DEBUG es False. DEBUG tiene valor predeterminado true.
SameSite=StrictRestringe su inclusión en contextos entre sitios.Siempre Strict. Hay escenarios de navegación desde otro sitio donde no viaja.
Max-AgeDuración en segundos de la cookie almacenada.86400 segundos: 24 horas. No renueva por sí solo la sesión.
ExpiresFecha absoluta de expiración de la cookie.Flask/Werkzeug puede derivarla de max_age. Max-Age tiene precedencia.
PathLimita las rutas donde se adjunta. No es una frontera de seguridad.El valor predeterminado de set_cookie es /.
DomainAmplía el alcance a un dominio y sus subdominios.Omitido: cookie vinculada al host que la establece.

Lee routes/auth_routes.py:123. El frontend usa credentials: "include" en templates/index.html:78. Eso permite incluir credenciales, pero no anula SameSite, Secure, el alcance de la cookie ni las reglas del navegador. Como tus URLs son relativas, frontend y API se sirven desde el mismo origen.

Cookie de sesión vs. cookie persistente

Sin Max-Age o Expires, la cookie se considera de sesión, aunque la restauración de sesiones del navegador puede recuperarla. Con una caducidad explícita puede conservarse al cerrar y abrir el navegador. En ambos casos el servidor debe verificar su propia expiración.

SameSite no es lo mismo que same-origin

El origen incluye esquema, host y puerto. El sitio usa el esquema y el dominio registrable, por lo que dos subdominios pueden ser del mismo sitio y tener orígenes diferentes. Strict, Lax y None son políticas de cookies, no controles de autorización. None requiere Secure en los navegadores actuales.

05Fundamentos

Sesiones persistentes y estado del servidor

Una sesión del lado del servidor es un registro que relaciona un identificador difícil de adivinar con un usuario autenticado. El navegador presenta el identificador; el servidor consulta el registro. Si el registro no existe o caducó, la credencial deja de funcionar.

  1. 01Login válido

    Se genera un UUID nuevo y un token CSRF.

  2. 02Servidor

    sessions[session_id] guarda usuario, rol y expires_at.

  3. 03Navegador

    Guarda sessionId con duración de 24 horas.

  4. 04Ruta protegida

    verify_auth busca la sesión y comprueba su fecha.

La creación está en routes/auth_routes.py:102. La verificación está en middleware/auth.py:32. No estás usando flask.session: implementaste un almacén propio. La sesión predeterminada de Flask, que guarda datos firmados en una cookie, es otro diseño.

Dónde viveQué contieneQué pasa al recargar o reiniciar
Cookie del navegadorSolo sessionId.Suele sobrevivir a recarga y cierre hasta que expire o se borre.
Memoria de Flask: sessionsUsuario, rol, CSRF, fechas.Se pierde al reiniciar el proceso; no se comparte automáticamente entre procesos.
Memoria de JavaScriptcsrfToken, authMethod y currentUser.Se pierde al recargar. init() consulta /auth/status y recupera /auth/csrf-token.
Memoria de Flask: usersCuentas y hashes.También se pierde al reiniciar; el admin de demostración se recrea.

Persistencia en dos capas

Conservar la cookie no basta: el servidor debe conservar el registro al que apunta. Tu implementación cumple el flujo de cookie persistente durante la vida del proceso, pero no tiene almacenamiento durable. Una base de datos para usuarios y un almacén compartido con TTL para sesiones permitirían abordar reinicios y múltiples trabajadores.

Caducidad, renovación y revocación

La sesión tiene expiración absoluta: 24 horas desde el login. No hay idle timeout (tiempo máximo sin actividad) ni sliding expiration (renovación de la ventana al usarla). verify_auth borra una sesión vencida cuando se intenta usar; no hay una limpieza periódica. Por eso el contador len(sessions) puede incluir registros caducados.

Revocar significa impedir el uso futuro antes de la expiración. Tu logout elimina el registro y manda borrar la cookie. Eliminar una cuenta también elimina sus sesiones cookie. Renovar un ID al autenticar ayuda contra la fijación de sesión; tu login genera uno nuevo, aunque no invalida automáticamente todos los IDs anteriores.

Para ampliar: OWASP · gestión del ciclo de vida de sesión.

JWT: estructura, validación y límites

El JWT firmado de tu proyecto es una cadena con tres partes separadas por puntos. Transporta afirmaciones sobre el usuario. La API verifica su autenticidad e integridad con una clave antes de confiar en ellas.

HEADER{"alg":"HS256","typ":"JWT"}Formato y algoritmo
.
PAYLOAD{"sub":"…","role":"user","exp":…}Claims o afirmaciones
.
MACHMAC-SHA256(…)Integridad con una clave compartida

Header y payload se representan con Base64url. El tercer segmento permite verificar el contenido. Leer un token no equivale a validarlo. Cambiar role en el payload sin generar un MAC válido produce un token que tu backend debe rechazar.

expMomento a partir del cual no se acepta.time.time() + 3600, en segundos Unix; PyJWT lo valida si está presente.

Tu emisor está en routes/auth_routes.py:89 y el verificador en middleware/auth.py:22:

token = jwt.encode(payload, config.JWT_SECRET, algorithm="HS256")

Fijar la lista ["HS256"] es una buena decisión: la política de algoritmos debe definirla el servidor. HS256 usa la misma clave para emitir y verificar; cualquiera que conozca esa clave puede emitir credenciales. RS256, en cambio, separa clave privada de firma y clave pública de verificación.

Requisito 6: firmado no es cifrado

Los comentarios etiquetan la firma HS256 como parte del requisito 6, pero no hay cifrado del payload. El email y el rol son legibles. Si el evaluador exige cifrar datos sensibles dentro del token, hay que implementar esa confidencialidad con una biblioteca adecuada o acordar una interpretación explícita del requisito. Minimizar datos es recomendable, pero no demuestra por sí solo que se implementó cifrado.

“Sin estado” tiene un alcance concreto

La validación JWT no busca un registro de sesión. Eso no significa que la aplicación no use almacenamiento: /user/profile consulta users. La lista de usuarios, los bloqueos y la administración siguen necesitando estado.

Expiración y claims obligatorios

Tu emisor siempre incluye exp, pero el verificador no usa options={"require": [...]}. Verificar un claim si existe y exigir que exista son controles distintos. Tampoco valida expresamente el esquema de email o role. Un token correctamente firmado al que le falta una clave usada con decoded[...] puede causar una excepción no cubierta por los dos errores de PyJWT que capturas.

CSRF: peticiones hechas en tu nombre

En CSRF, otro sitio intenta provocar una acción contra tu aplicación aprovechando que el navegador puede adjuntar credenciales automáticamente. La víctima ya está autenticada. El atacante necesita que se ejecute la acción, aunque no pueda leer la respuesta.

  1. 01Sesión abierta

    La víctima tiene sessionId en su navegador.

  2. 02Otro sitio

    Intenta inducir una petición que modifica datos.

  3. 03Credencial ambiental

    El navegador podría adjuntar cookies según sus políticas.

  4. 04Defensa

    El servidor exige un token CSRF que el otro sitio no conoce.

Tu patrón: token sincronizado con la sesión

middleware/csrf.py:18 genera un UUID. El login lo guarda en sessions y lo devuelve en JSON. El frontend conserva csrfToken; req() añade X-CSRF-Token para métodos distintos de GET cuando está en modo cookie.

middleware/csrf.py:22 comprueba primero el método de autenticación. Si es cookie y la petición cambia estado, compara el header con el token de esa sesión. Un token de otra sesión debe fallar. El secreto no debe ir en URLs ni registrarse en logs.

POST /auth/logout HTTP/1.1
Cookie: sessionId=<id-sesion>
X-CSRF-Token: <token-de-esa-sesion>
Content-Type: application/json

¿Por qué hay /auth/csrf-token?

Después de F5 la cookie permanece y la variable JS desaparece. init() consulta el estado y recupera el CSRF por una ruta autenticada. Con la política de mismo origen, otro sitio no puede leer libremente esa respuesta. Una configuración CORS demasiado permisiva podría debilitar esa premisa.

JWT no es una exención universal

El motivo para omitir el token CSRF aquí es el envío explícito de Authorization: Bearer. Si movieras el JWT a una cookie de envío automático, tendrías que reevaluar CSRF. Tampoco debes tratar CORS o SameSite como sustitutos universales del análisis de las rutas.

Cobertura real

verify_csrf protege POST /auth/logout y DELETE /admin/users/<id>. No se aplica a /auth/login ni /auth/register. El uso de JSON y SameSite reduce ciertos vectores, pero el requisito de proteger solicitudes de cambio debe revisarse ruta por ruta, incluyendo login CSRF y validación de Origin. No se demostró un ataque ejecutable contra esas dos rutas.

El token CSRF no prueba que el usuario sea administrador y no sustituye la sesión. Un XSS dentro del propio origen puede leerlo o pedirlo, por lo que XSS y CSRF requieren defensas distintas.

XSS: cuando datos terminan como código

XSS ocurre cuando un dato no confiable acaba interpretándose como código en el navegador. Puede ser almacenado (se guarda y se muestra después), reflejado (vuelve en la respuesta) o basado en DOM (JavaScript del cliente lo coloca en un lugar peligroso).

Sigue los datos en tu aplicación

  1. 01Entrada

    Email recibido en el JSON del registro.

  2. 02Transformación

    sanitize() usa html.escape(..., quote=True).

  3. 03Almacenamiento

    Se guarda el email transformado en users.

  4. 04Salida

    listUsers() concatena una tabla y la asigna a innerHTML.

En utils/sanitize.py:5 se escapan caracteres para HTML. Eso es escape de salida HTML aplicado antes de guardar, no una sanitización universal. En templates/index.html:71 y templates/index.html:149 usas textContent, que trata el contenido como texto. Es una buena elección.

La tabla de templates/index.html:124 usa innerHTML. El escape actual del email mitiga ese punto de inserción HTML; no se confirmó una explotación ahí. Sin embargo, depende de que todos los datos conserven esas garantías. Es más robusto construir nodos y asignar textContent a email, rol e ID, y registrar eventos con addEventListener.

// Patrón ilustrativo de salida segura, no aplicado al repositorio
const cell = document.createElement("td");
cell.textContent = user.email;
row.appendChild(cell);

Validar, normalizar, escapar y sanitizar

Validar decide si el dato es aceptable; normalizar lo convierte a una representación acordada; escapar impide que caracteres adquieran significado en un contexto de salida; sanitizar HTML elimina contenido no permitido cuando de verdad se admite HTML. Escapar HTML no hace seguro un valor usado como JavaScript, URL o SQL.

Guardar emails escapados mezcla almacenamiento y presentación. Un diseño más claro valida y guarda el valor canónico y luego lo inserta de forma segura en cada salida. En tu código, un email no textual puede atravesar sanitize y fallar al llamar .lower(); eso es una falta de validación de tipos, no una defensa XSS.

Defensa por capas

Usa destinos de texto, codificación contextual y una política CSP compatible con la interfaz. Una CSP estricta no puede añadirse sin revisar tus manejadores onclick y scripts inline: normalmente habrá que extraerlos o usar nonces/hashes adecuados. HttpOnly limita la lectura de la cookie, pero un XSS todavía puede llamar a tus rutas autenticadas.

Sigue las peticiones paso a paso

A · Registro

  1. register(event) evita el envío tradicional del formulario.
  2. req() serializa email y contraseña como JSON y llama a POST /auth/register.
  3. Flask lee el cuerpo, escapa y normaliza el email; valida presencia, formato, longitud mínima y duplicado.

  1. El radio seleccionado produce authMethod: "cookie".
  2. El backend valida presencia, consulta bloqueo, busca usuario y ejecuta checkpw.
  3. Un fallo se cuenta. Un éxito limpia intentos previos.
  4. Genera sessionId y csrfToken; guarda fechas, identidad y rol en sessions.
  5. Responde con Set-Cookie y con csrfToken, role y authMethod en JSON.
  6. El navegador conserva la cookie; el frontend conserva el token CSRF y actualiza la pantalla.

  1. getProfile() llama a GET /user/profile. No necesita token CSRF porque es una lectura.
  2. El navegador adjunta sessionId. verify_auth busca la sesión y rechaza la inexistente o vencida.
  3. El middleware fija g.user, g.auth_method y g.session_id.
  4. La ruta busca el usuario por el ID autenticado y devuelve campos públicos; nunca devuelve el hash.

D · Login y perfil con JWT

  1. La contraseña se verifica igual que en cookie, pero se elige authMethod: "jwt".
  2. Se emite un token HS256 con sub, email, role y exp.
  3. El frontend guarda el token en su variable token.
  4. req() añade Authorization: Bearer a las siguientes peticiones.
  5. verify_auth valida el JWT y llena g; no consulta sessions.
  6. La ruta de perfil sí consulta users. Puede responder 404 aunque la firma sea válida, por ejemplo si esa cuenta ya no existe.

E · Eliminar una cuenta como administrador

  1. 01Autenticación

    Credencial válida; si falla: 401.

  2. 02RBAC

    Rol admin; si falla: 403.

  3. 03CSRF

    Si cookie, token correcto; si falla: 403.

  4. 04Operación

    Rechaza autoeliminación, verifica existencia, borra sesiones y cuenta.

El frontend solo muestra Eliminar para usuarios no admin, pero la API permite a un admin borrar otro admin si existe y conoce su ID. La única prohibición explícita del backend es borrar su propia cuenta. Distingue política de interfaz de política del servidor.

F · Logout y recuperación

Con cookie, logout() del backend elimina la sesión de g.session_id y envía una cookie vencida. Con JWT no hay una sesión JWT que borrar. La interfaz limpia las variables después de la llamada. Al cargar de nuevo, init() consulta /auth/status y, si encuentra una cookie válida, pide /auth/csrf-token.

Caso real: se mezclan los dos métodos

Entrar primero con cookie y luego con JWT no borra el registro cookie anterior. El navegador sigue pudiendo enviar sessionId. verify_auth prioriza Bearer, y el logout JWT no tiene g.session_id, por lo que no elimina aquel registro; sí manda borrar la cookie del navegador. Además, tras recargar mientras existe esa cookie anterior, la interfaz puede recuperar la identidad cookie en vez de la identidad del último JWT. Define cómo quieres manejar el cambio de método.

Caso real: logout rechazado

El frontend limpia sus variables aunque /auth/logout responda un error HTTP. Si el CSRF falta o falla, el servidor no borra la sesión; la pantalla puede decir “No autenticado” y al recargar recuperar la sesión. Hay que condicionar la limpieza al resultado o manejar claramente el fallo.

Un matiz serio de la revocación JWT

Al eliminar una cuenta se borran sus sesiones cookie, pero no se invalidan sus JWT. /user/profile respondería 404 porque busca el usuario; /auth/status todavía puede informar authenticated=true. Si se elimina a un administrador mediante otro admin, su token mantiene el rol firmado y el middleware de las rutas admin no comprueba que la cuenta siga existiendo. La interfaz no ofrece borrar admins, pero el backend sí permite borrar otro admin.

Reiniciar no equivale a revocar todo

Si el proceso reinicia con la misma clave, los JWT anteriores pueden seguir validándose hasta exp. Los IDs de cuentas se pierden y el admin seed recibe otro UUID. El viejo token admin aún porta role=admin. Esa combinación muestra por qué hay que separar integridad del token de vigencia de la cuenta.

16Ampliación

Conceptos avanzados que conviene defender

Estos diseños no están implementados en tu repositorio. Conocerlos te permite responder qué cambiarías para una aplicación real sin atribuirle capacidades que todavía no tiene.

Access token y refresh token

Un access token corto limita el tiempo de exposición de una copia robada. Un refresh token sirve para obtener nuevos access tokens sin volver a introducir la contraseña. Debe tener almacenamiento protegido, caducidad y revocación. La rotación consume uno y emite otro; reutilizar uno ya consumido puede indicar robo. Implementar refresh agrega complejidad y normalmente estado en el servidor.

Referencia: RFC 9700 · protección y rotación de refresh tokens.

Revocación y compromiso con “sin estado”

Una denylist por jti, una versión de credenciales por usuario o una consulta de cuenta activa permite rechazar tokens antes de exp, pero obliga a consultar estado. Cambiar la clave invalida muchos tokens a la vez y requiere un plan de rotación. Eliminar el token en un cliente solo elimina esa copia.

JWS, JWE y gestión de claves

Tu JWT es una representación firmada/MAC de estilo JWS. JWE aporta cifrado; su serialización compacta tiene cinco segmentos. La biblioteca debe verificar también la integridad y usar algoritmos permitidos. Las claves de cifrado y de firma deben gestionarse según su propósito. Un kid identifica una clave dentro de un conjunto confiable; no debe dar libertad para cargar claves desde ubicaciones arbitrarias.

Referencia: RFC 7516 · JSON Web Encryption.

OAuth 2.0, OpenID Connect y SSO

OAuth trata de autorización delegada: dar a una aplicación acceso limitado sin entregarle la contraseña del usuario. OpenID Connect añade identidad sobre OAuth y define el ID token. Un ID token para un cliente no sustituye automáticamente al access token de una API. SSO permite reutilizar una sesión del proveedor de identidad entre aplicaciones. Tu login local no implementa ninguno de esos protocolos.

Referencia: OpenID Connect Core · identidad sobre OAuth 2.0.

MFA y recuperación

MFA combina factores independientes. Una segunda contraseña no crea un segundo factor. Passkeys/WebAuthn usan credenciales de clave pública vinculadas al sitio; TOTP usa códigos temporales. La recuperación de cuenta debe recibir el mismo cuidado: tokens de un solo uso, vigencia corta, almacenamiento seguro, mensajes que reduzcan enumeración y una política de cierre de sesiones tras cambio de contraseña.

Referencias: MDN · WebAuthn y OWASP · recuperación de contraseña.

Origen, CORS y preflight

CORS define qué respuestas puede leer JavaScript desde otro origen. Algunas peticiones exigen una comprobación previa OPTIONS, por ejemplo por ciertos headers. No impide que un cliente fuera del navegador llame a la API, y no toda petición entre orígenes necesita preflight. Con cookies entre orígenes se requiere una configuración coherente de credenciales, orígenes permitidos y atributos; no basta con credentials: "include". Tu aplicación actual es de mismo origen y no declara middleware CORS.

Cabeceras de defensa

Content-Security-Policy limita recursos y ejecución de scripts; frame-ancestors puede prevenir incrustaciones no autorizadas. Strict-Transport-Security refuerza el uso de HTTPS una vez recibido válidamente. X-Content-Type-Options: nosniff reduce interpretaciones incorrectas del tipo. Cache-Control: no-store resulta relevante para respuestas con credenciales o información sensible. Ninguna reemplaza la autorización.

Referencia: MDN · Content-Security-Policy.

Escalabilidad y concurrencia

Con múltiples procesos, los diccionarios no representan una base común. Los límites de intentos necesitan incrementos atómicos; los emails necesitan una restricción de unicidad en almacenamiento; las sesiones necesitan TTL. Las operaciones “comprobar y después escribir” pueden sufrir carreras. No basta con que una demo de un solo proceso parezca consistente.

Auditoría y mínimo privilegio

Registra eventos de éxito/fallo, revocación, cambios de rol y operaciones administrativas con fecha y un identificador de correlación. Evita contraseñas, tokens y secretos. El contador de intentos es una estructura operativa, no un historial de seguridad: tu login correcto lo borra. Minimizar privilegios y datos en tokens limita el daño si una credencial se filtra.

Para ampliar: RFC 7519 · formato JWT y claims.

Es una aplicación Flask que registra usuarios con bcrypt y permite autenticarse con una sesión de servidor identificada por cookie o con un JWT HS256 en Authorization. ¿Dónde está la sesión?

El registro está en sessions, en la memoria del proceso. La cookie solo lleva su ID. No uso flask.session ni guardo todo el perfil dentro de la cookie.

¿Cómo sigo conectado después de cerrar el navegador?

La cookie tiene Max-Age de 24 horas. Al regresar, el navegador puede enviarla y el backend busca el registro vigente. Si Flask reinició y perdió sessions, la cookie sola no alcanza.

¿Puedo leer tu JWT sin la clave?

Sí, el header y el payload están codificados, no cifrados. La clave se usa para generar/verificar el MAC HS256; la confidencialidad del payload no está implementada.

¿Por qué guardar un hash y no cifrar la contraseña?

Solo necesito verificarla. El hash de contraseñas evita mantener una clave de descifrado que revele todas las contraseñas. bcrypt añade salt y coste; las contraseñas débiles todavía pueden adivinarse.

¿Qué diferencia hay entre 401 y 403?

401 significa que no tengo una credencial aceptable. 403 significa que rechazo el acceso por permiso o por otra comprobación como CSRF. En mi implementación un user válido recibe 403 al acceder a /admin.

¿HttpOnly impide XSS?

No. Impide leer esa cookie desde JavaScript. Un XSS todavía puede ejecutar peticiones autenticadas y leer datos que la página pueda leer.

¿Por qué usas CSRF con cookie?

Porque el navegador puede adjuntar la credencial automáticamente. La API exige además un secreto de la sesión en X-CSRF-Token para las operaciones protegidas.

¿Todo JWT evita CSRF?

No. En mi código la exención depende de enviarlo explícitamente en Authorization. Si lo transporto en una cookie automática, debo analizar CSRF otra vez.

¿Qué pasa al recargar en cada modo?

Cookie: init() consulta status y recupera CSRF. JWT: la variable se pierde, así que no se restaura si no hay otra cookie activa.

¿Logout invalida el JWT?

No. La interfaz elimina su copia, pero no existe denylist ni versión de token. Otra copia puede funcionar hasta exp mientras la clave y las políticas de validación sigan aceptándola.

¿Qué se ejecuta primero al eliminar un usuario?

verify_auth, luego require_role("admin"), luego verify_csrf y finalmente delete_user. Así los controles siguientes tienen la identidad y el método disponibles en g.

¿Cómo evitas que un usuario se haga admin?

El registro asigna role=user en el servidor y las rutas admin verifican el rol autenticado. Manipular botones no cambia los permisos. Proteger JWT_SECRET es esencial porque conocerla permitiría emitir roles firmados.

Se incrementa a cinco y se fija locked_until. Ese intento aún devuelve 401. El siguiente se bloquea antes de comparar la contraseña y devuelve 429.

¿Qué pasa si eliminas una cuenta con JWT activo?

Las sesiones cookie se eliminan. El JWT no se revoca: status puede seguir diciendo true y profile devuelve 404 al no encontrar la cuenta. Si el rol era admin, las rutas admin necesitan una comprobación adicional de vigencia para revocarlo.

¿El JWT hace innecesaria la base de datos?

No. Evita consultar una sesión en la validación diseñada así. Los perfiles y permisos vigentes pueden requerir almacenamiento; el sistema todavía tiene datos y estado.

HS256 firma mediante HMAC pero no oculta email o rol. Debo implementar el cifrado solicitado con una solución estándar o acordar una interpretación explícita, sin afirmar que Base64url o HTTPS cifran el token almacenado.

Es un objeto del contexto actual de Flask; en una petición transporta identidad y método entre decoradores y ruta. No conserva el login entre peticiones.

6# Req. 8 - Protección CSRF (Cross-Site Request Forgery).
7#
8# FLUJO:
9#   1. Al hacer login con cookie, el servidor genera un csrfToken y lo devuelve en el body JSON.
10#   2. El cliente guarda el csrfToken en JavaScript (no en cookie → un atacante cross-site no puede leerlo).
11#   3. En cada petición que cambia estado (POST/PUT/DELETE), el cliente incluye el header X-CSRF-Token.
12#   4. El servidor verifica que coincida con el almacenado en la sesión.
13#

15#   El token JWT va en el header "Authorization", que un sitio externo no puede enviar automáticamente.
